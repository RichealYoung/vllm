# Final evaluation: tokenization + block-hash reuse (text)

This page evaluates the final text version of both optional mechanisms together, **tokenization reuse plus block-hash reuse (T+H)**, against the same upstream without either. It adds to the [block-hash reuse follow-up](../README.md) and does not replace its earlier measurements. All results compare T+H with the baseline; the incremental effect of hash reuse alone was not rerun (see the follow-up page for that earlier result).

## Setup

Qwen3-0.6B (`c1899de2`) on one RTX 3090, FP16, maximum length 40960, four sequences, 4096 batched tokens, 18 GiB KV cache, prefix caching, chunked prefill and async scheduling enabled. F uses 512 MiB for tokenization history and 128 MiB for hash history; nothing else differs. Each run is a fresh server with the same warmup, including two short reuse conversations under a separate cache salt, followed by a prefix-cache reset. Configurations are paired in four blocks ordered N→F, F→N, N→F, F→N. The run is the unit of repetition; no significance claim is made.

## Results

**Synthetic growing histories (scenario A).** 4 sessions × 20 turns, 16K–35K input tokens, frozen messages, sent strictly one at a time, 448 output tokens:

| Metric (later turns) | Baseline | T+H | Change |
|---|---:|---:|---|
| Mean time to first output | 326 ms | 223 ms | **−102.8 ms (−31.5%)**; blocks −27.8% to −33.7% |
| P95 time to first output | ~424 ms | ~286 ms | lower |
| Mean end-to-end latency | ~3.24 s | ~3.14 s | about −3% |

Instrumented runs with 16 output tokens show where the time goes (medians of later turns):

| Stage | Baseline | T+H |
|---|---:|---:|
| Tokenization | 88.6 ms | 8.1 ms (new suffix only) |
| API-side input processing | 101.3 ms | 22.5 ms |
| Initial block hashing | 13.5 ms | 0.6 ms (new blocks only) |
| EngineCore request preprocessing | 13.9 ms | 4.3 ms |
| Added reuse work (match, validation, history) | — | ≈ 5.1 ms in total |

The largest added items are the exact token comparison for hash reuse (1.3 ms), joining reused and new token IDs (0.5 ms), sizing stored hashes (0.6 ms) and releasing the previous snapshot (0.6 ms).

**Real coding-agent trajectories (scenario E).** 16 OpenHands trajectories (702 requests) from [nebius/SWE-rebench-openhands-trajectories](https://huggingface.co/datasets/nebius/SWE-rebench-openhands-trajectories) (CC-BY-4.0, revision `35455389`), generated by Qwen3-Coder-480B on real GitHub issues. Each request resends the full history with tool definitions. Recorded tool calls, file views, diffs and command output are replayed unchanged; output length follows the recorded reply (median 74 tokens). Inputs grow from about 7K to 41K tokens (median 24K) by a median of 459 tokens per step. Four agents run at once, in four batches, with seeded tool-execution pauses (median 2 s). Native prefix-cache hits were never lost at this concurrency.

| Metric | Baseline | T+H | Change |
|---|---:|---:|---|
| Mean time to first output, steps after the first | 285 ms | 198 ms | **−86.4 ms (−30.3%)**; blocks −28.5% to −32.4% |
| P95 time to first output | ~507 ms | ~394 ms | −113 ms |
| Mean end-to-end latency | ~2.55 s | ~2.50 s | about −2% |

The saving grows with input length, from about 41 ms below 12K tokens to about 142 ms above 36K. Request timelines show it comes from frontend processing (97 → 20 ms) and EngineCore preprocessing (13 → 4 ms); with four agents it was not absorbed by scheduling delay.

**Worst cases.**

- *No usable history*: the same trajectories with a new session for every request. T+H was slower by **13.1 ms (4.6%)** on average (blocks 6.6–20.7 ms), and P95 by 28 ms. Every request is still stored, so both histories fill their budgets and keep evicting. About 8.7 ms is accounted for: full token-ID validation and eviction (≈ 7.7 ms) and more frequent garbage collection (≈ 1 ms on average, one pause of 73 ms). The rest is within the run-to-run spread. Clients should not send a new random session for each request.
- *Edited history* (CPU measurement): when an edit near the start of the conversation leaves almost nothing reusable, T+H costs 3.5–6.4 ms more than normal processing (52–95 ms). When the edit is in the second half, or a middle tool call and its result are removed, it still saves 16–77 ms.

**Correctness during the measurements.** Prompt token counts and cached-token counts matched request by request between baseline and T+H in every pair. An offline check sent all 702 agent requests through the tokenization and hash histories. Every token ID and every block hash matched normal computation; tool-call markers in the Qwen3 template served as safe reuse boundaries.

## Limitations

One model, one GPU, one API process. The synthetic histories are generated text without tools; the agent replay does not feed generated outputs back, assumes append-only histories (no context condensing), and uses chosen concurrency and pause settings. The baseline cost profile also found that native hashing runs about 2.5× slower in the server than offline; savings are compared only within paired runs. These are author measurements, not upstream CI or a production capacity claim.
